## CRITICAL security finding (verified, unfixed)

Anonymous platform-takeover chain:
1. `POST /api/tenants` (`src/app/api/tenants/route.ts:59`) — auth is OPTIONAL;
   `isSystemAdmin` defaults false and execution continues (self-serve onboarding).
2. `tenantId` is client-supplied (`:83`) and validated only by
   `^[a-z0-9-]+$` in `onboardInstituteSchema`. `"system"` passes. No reserved-slug
   check exists anywhere in `src/lib/`.
3. Login yields a JWT with `tenantId: "system"`, `role: "ADMIN"`.
4. `src/lib/api-auth.ts:126` (`user.tenantId?.toLowerCase() === "system"`) sets
   `isPlatformAdmin`, then `:133` returns early — **skipping all RBAC**.
5. Same literal check is copy-pasted into `middleware.ts:63` and five
   system-admin route gates, so `/system-admin` UI + all cross-tenant APIs open up.

Fix shape: require platform-admin auth on `POST /api/tenants`, reserve the
`system` slug, and replace every `tenantId === "system"` string comparison with an
explicit role allowlist.

## Secondary auth gaps (verified)

- `requireApiAccess` returns authenticated-but-unchecked when
  `getPermissionModuleForApiPath` maps to `null` (`api-auth.ts:150-152`).
  Affects `/api/audit-logs`, `/api/homeworks` (no case in the switch).
- 6 of 7 `/api/reports/*` routes bypass `requireApiAccess` entirely and use raw
  `getAuthContext`. Tenant scoping is correct there; permission checking is absent.
- `getAuthContext(..., { allowTrustedHeaders: true })` trusts `x-user-id` /
  `x-tenant-id` and never verifies the JWT (`auth.ts:37-54`). Currently unreachable
  — no caller — but is a live bypass if anyone passes that option.
- Tenant scoping itself is otherwise CLEAN across 25+ sampled CRUD routes.
  The isolation rule holds; the privilege model above it does not.
